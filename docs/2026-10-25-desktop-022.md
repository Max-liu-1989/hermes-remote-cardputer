# 2026-10-25 · 适配 Hermes 桌面端 0.22.x

## 为什么改

桌面端从 0.22.x 起不再由 Electron 拉起 `hermes serve`，改成 launchd 托管的
`gateway run --external-supervisor`。后端的端口、凭证、协议一起变了：

| | 旧（≤ 0.22.2） | 新（0.22.4） |
|---|---|---|
| 后端进程 | Electron 起 `hermes serve --port 9119` | launchd 起 `gateway run`，端口随机 |
| 端口发现 | `ps eww` 找 `HERMES_DESKTOP=1` 的进程 + `lsof` | `~/.hermes/gateway.sock` 的 `identify` → `api_origin` |
| 会话 token | 注入后端子进程环境变量 | 进程内存随机值，首页不发布（`withhold_session_token`） |
| 挂会话 | `session.activate` | `session.resume` |
| 待答请求 | `srq-` 帧推送 / `open_requests` | `session.resume` 快照里的 `prompts` 数组 |
| 作答 | `request.answer {id, result}` | `approval.respond` / `clarify.respond`（`prompt_id` + `execution_generation`） |

桥原来的 discovery 在新后端上必然返回 `None`，然后回落到默认的 9119（没人监听）——
板子上就是 `bridge offline`。

## 怎么修的（不改 Hermes 源码）

1. **固定 token**：在 `~/Library/LaunchAgents/ai.hermes.gateway.plist` 的 `EnvironmentVariables`
   里加 `HERMES_DASHBOARD_SESSION_TOKEN`，值放 `~/.hermes-remote/backend.token`（0600）。
   gateway 的 `_SESSION_TOKEN` 就是从这个环境变量读的，回环地址的 `/api/ws` 拿 `?token=` 与它做常量时间比较。
2. **重新加载 plist**：`launchctl kickstart -k` **不会**重读 plist，要
   `launchctl bootout gui/$(id -u)/ai.hermes.gateway` 再 `launchctl bootstrap gui/$(id -u) <plist>`。
   验证：`launchctl print gui/$(id -u)/ai.hermes.gateway | grep HERMES_DASHBOARD_SESSION_TOKEN`。
3. **端口发现**：`hermes_remote/desktop_discovery.py` 先连 `gateway.sock` 发
   `{"protocol":1,"verb":"identify","id":1}`，从 `result.api_origin` 取端口；老的 `ps eww` 逻辑保留作回退。
4. **挂会话**：`session.resume`（回 `-32601` 时再试 `session.activate`，兼容旧后端）。
5. **待答请求**：每 5 秒 `session.resume` 扫 `prompts`。**注意 `pending` 是排队中的用户输入，
   不是审批请求**——两者字段形状相似，看错会永远拿不到卡。canonical 给的是平铺的
   `question` / `choices`，渲染层要的是 `questions: [{qid, question, choices}]`，
   转换时必须包一层，否则卡片能上屏但一个选项都不显示（按数字键毫无反应，且没有报错）。
6. **作答**：`approval.respond {session_id, execution_generation, prompt_id, choice}`、
   `clarify.respond {session_id, execution_generation, prompt_id, answer}`。
   `answer` 是单个字符串（空串 = 跳过）。`approval.pending` 返回的 `request_id` 属于旧接口，
   和 canonical 的 `prompt_id` 是两套 id，混用会得到 `4001 invalid_params`。

## 验证范围（照实写）

| 能力 | 状态 |
|---|---|
| 后端发现 + 鉴权 | 实测通过（WS 握手、`gateway.ready`） |
| 会话列表 / 跟随当前会话 | 实测通过 |
| 会话状态、助手回复正文 | 实测通过 |
| clarify 卡上屏 → 板子上按 1 → 回传 → 确认页 | **实测通过**（审计 `request.received` / `request.answered`，agent 侧收到答案） |
| approval 卡 | 与 clarify 同一条路径，**未在真实审批上验证**（本机 smart approval 自动放行，造不出待批） |
| 固件 / 语音 | 本次未改动 |

## 已知限制

- 桥一次只挂一个会话；别的会话的 clarify 要等桥跟随过去才会上屏。
- `session.resume` 的快照包含完整 messages，5 秒一次是延迟与带宽的折中；更密的轮询会拖住渲染 ticker。
- Hermes 更新可能再次改写后端启动方式；上面四步是「不改源码」的接入方式，升级后要重新核对
  `gateway/run_api.py` 与 `gateway/drain_control.py` 里的方法表。
- 回环明文 WS、无 TLS——威胁模型仍是「可信局域网」。
