## 三、第一优先级：修复审批安全（处理规则 1–7）

| 规则 | 状态 | 落点 |
|---|---|---|
| 1. 命令缺失/为空/类型错误/无法完整查看 → 设备端禁止批准 | **已改** | `safety.approval_facts()` + `bridge._on_prompt_key()` 的 `if not facts.valid` 分支 |
| 2. 屏与按键共用同一份校验后的审批信息 | **已改** | `PendingRequest.approval` 是唯一入口；`state._approval_view` 不再读 `params` |
| 3. 高风险操作要二次确认；二次确认不能弥补信息缺失 | **已改** | 无效请求连第一次都不行；有效但不危险才单击放行 |
| 4. 不靠正则把任意 shell 判安全；未知工具保守处理 | **已改** | 终端类工具默认可疑，只读命令白名单才免二次确认 |
| 5. 确认绑定会话/请求/内容；变化/切换/过期/已处理后失效 | **已改** | 绑定 `digest = sha1(tool+命令)`；请求切换、内容变化、断线重连都清上膛 |
| 6. 拒绝明确可用；断线重连不得补发旧批准 | **已改** | 拒绝不受翻页/内容校验限制；断线清 arm；重连不重放队列；后端 `expired` 不写“已发送” |
| 7. 后端同时校验请求有效性与处理状态 | **已改（客户端侧）** | 作答走 `request.answer` RPC，按后端 `ok`/`expired` 判结果并落审计 |

**验收覆盖**（`tests/test_approval_model.py`，19 条）：

- 输入：`command` 缺失、空串、纯空格、`int`、`dict`、`list`、超长（>540 字符）；
- 交互：连续按键、翻页未完成、翻完再两次确认、内容变更后旧确认、断线后旧确认；
- 边界：description 里写 `rm -rf` 但无 command → 仍然无效（不能靠描述骗判定）。

## 四、第二优先级：身份识别与通信保护

| 要求 | 状态 | 说明 |
|---|---|---|
| 屏上可辨认项目/会话/工具/内容 | **已改** | 标题行 = 会话标题；审批页首行 = 危险判定 + 工具名；正文 = 命令（可翻页） |
| 长命令可完整查阅，否则禁止批准 | **已改** | 翻页（`fn`/`back`），翻完才可批；>8 页判无效 |
| 核查明文连接与 URL 携 token | **部分** | token 已离开 URL；访问日志本就关闭；**TLS 未做** |
| 设备凭据撤销与更新 | **已改** | `hermes_remote.cli rotate-token`（0600，不回显，旧 token 立即失效） |
| 审计不含凭据、能逐条对上 | **已改** | 审计只有 `request.*` / `voice.*`；`AuditNoCredentialTests` 守着；`delivery` 字段记录后端结果 |

**为什么 TLS 这轮没做**：桥跑在 Mac 上给板子做服务端，要做到“加密 + 验证对端身份”，
需要给桥签一张自签证书、把指纹烧进固件、并处理首次信任与轮换。这一整条**没有硬件就无法验证**
（证书校验失败的表现和 WS 握手失败长得一样，盲改等于制造一个未经验证的路径）。
按整改建议“每项验证要有证据”的标准，这轮先做到“凭据不进日志/不进 URL”，TLS 单列为下一步。
