### 真实审批闭环（2026-10-18 实机 + 真后端）

| 场景 | 操作 | 结果 | 证据 |
|---|---|---|---|
| 危险命令放行 | 板子按 `1` 两次（第一次上膛） | 后端收到 `once`，命令执行 | 审计 `request.answered via=device choice=once delivery=ok age_s=36.7`；屏上帧 1793 B → 2015 B（确认页） |
| 拒绝 | 板子按 `2` 一次 | 后端收到 `deny`，命令**未执行** | 审计 `via=device choice=deny delivery=ok age_s=8.6`；工具返回 `BLOCKED: Command denied by user` |
| 键位固定 | 按 `2` 期望拒绝 | 得到 `deny`（修复前是 `session`） | 见下「键位顺序」缺陷 |

**键位顺序缺陷（真机发现，已修）**：审批选项原来按后端返回顺序编号（`once/session/always/deny`），
于是 `2` = “本会话都同意”。用户想拒绝按了 2，直接把整个 `-e/-c` 模式放行了一整个会话，
后续同类命令不再弹审批。现在 `ApprovalFacts` 之外再加一层固定键位表
（`safety.approval_key_map`：**1=同意一次、2=拒绝（永远存在）、3=本会话、4=永久**），
渲染与按键共用它，并有 3 个回归用例锁住；真机按 2 已确认得到 `deny`。

## 附：真机联调中发现的 7 个缺陷（已修，详见 README §0 第三轮）

1. 网关丢弃带 `id` 的 `srq-` 询问 → 推送永远到不了桥；
2. 广播无超时 → 一个不读的客户端拖死渲染循环；
3. 板子不清 seq → 桥重启后画面冻结 + `RECONNECTING`；
4. 状态行按秒显示时长 → 每秒整屏重发（闪屏）；
5. esptool stub 丢包 → 第二次烧录失败；
6. AP 兜底写不了 token、串口窗口只有 8 秒；
7. 串口配网脚本不等设备重新枚举（`Device not configured`）。
